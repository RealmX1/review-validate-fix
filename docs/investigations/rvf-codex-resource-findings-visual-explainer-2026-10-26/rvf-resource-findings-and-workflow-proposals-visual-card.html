为什么有两个 Token 比例？

模型重复读取已经缓存的上下文，也会产生 Token 记录。“全部 Token”把它算进去；“新读入＋输出”扣掉缓存读取。复盘的缓存比例较低，所以换一种口径，占比会变大。

这是字数与用量口径，不是美元账单或订阅额度比例。17 轮主要组件可计量；健康探测用量仍有缺失，比例属于已观测口径。若只遗漏非负的探测用量，当前比例是全量占比的上界。

方案取舍：保守、推荐、进取
方案做法取舍
保守补齐计量，继续每轮 LLM 复盘。变动小、反馈及时，复盘调用次数基本不变。
推荐先小范围试点：普通轮次每周或累计 20 轮聚合；需要新推理的异常与显式请求仍即时分析。有机会减少重复阅读、发现跨轮模式；普通轮次的叙事复盘会延迟。
进取跨项目统一资源预算、调度和建议执行。可能获得更大收益，但状态、授权和恢复面明显扩大，先不作为首轮实现。

7 天／20 轮是提案的试点默认值，尚未变更任何运行配置。批量包最多 20 轮；每轮保留 run ID、版本与输入摘要，批量结论必须能追回原始证据。

恢复和验收：由机器处理哪些缺口？
  • 归档／计数失败：复用现有恢复入口，只重验或补记失败部分，保留旧失败历史；不重新创建 RVF，不重复启动已完成的 LLM。
  • 用量暂缺：记录 unavailable 与原生会话身份、读取游标和重验条件；新记录到达时幂等补账，其他轮继续。
  • 批量中断：持久保存批次成员与输入摘要，按批次互斥认领；重启只续未完成项，不重复提交建议。每个证据代次最多三次自动尝试，证据未变化不无限重试。
  • 新建议：先核对当前代码及已存在任务。在既有授权内执行可逆动作；只有真实取舍、新权限或人独有的信息进入人工决策。
  • 对照试验：在相近项目与改动风险下比较逐轮／批量策略；纳入批量自身、重试和建议核实的用量。保留原 reviewer 和必需验证，检查已知问题识别及建议可追溯性。
  • 后续核验条件：下一次自然发生的 Codex RVF 产生与部署版本绑定的归档回执后，验证正式完成和恢复能力；本次没有额外触发新 RVF。
提案判断与证据边界

意图：解释历史观察，并提出流程更新，不实施生产变更。决策：ESCALATE——值得推进为分阶段设计与试点，尚不是已批准的完整实施契约。

已有能力：正式归档授权、校验、有限重试与恢复已经存在，不重新开发。计量已有边界与主／子会话观测，增量目标是补齐 reviewer、后台 Analyze 与探测。

前提：现有源码把 reviewer 与后台 Analyze 用量标为 unavailable；历史样本显示逐轮复盘确有成本。批量必然省钱、复盘失败率仍为 17/18、或缩减 reviewer 可以保持质量，都没有被证明。
