## 当前 bundled hooks 为何仍注册

RVF 的两份宿主 manifest 共享一个插件目录，包含 `hooks/hooks.json` 的 Stop、UserPromptSubmit、PostToolUse。Codex manifest 当前没有显式 `hooks` 字段，因而按约定发现该文件。三条脚本服务 Claude Code；Codex 的正式 RVF 入口仍为全局的 Stop 和 UserPromptSubmit。

源码入口（基线提交中的位置）：

- [共享插件构建](../../../scripts/install_to_codex.py)：`build_developer_marketplace_release` 第 303 行起复制同一 payload；第 830 行调用 bundled 停用函数。
- [Codex manifest](../../../plugins/review-validate-fix/.codex-plugin/plugin.json) 与 [Claude manifest](../../../plugins/review-validate-fix/.claude-plugin/plugin.json)：两者均未显式声明 hooks。
- [bundled 定义](../../../plugins/review-validate-fix/hooks/hooks.json)；[Claude 入口守卫](../../../plugins/review-validate-fix/hooks/_claude_hook_entry.py) 第 108 行：仅有正向 Codex rollout 路径证据时返回 foreign，不能概括为“任意非 Claude 输入恒定 no-op”。
- [现有停用逻辑](../../../core/codex_bundled_plugin_hook_suppression.py) 第 163、274 行：修改 enabled，保留已有信任；不会阻止定义被发现。

9 月 11 日只读复核：Codex manifest、installer、停用模块和入口守卫与实际部署来源一致；当前缓存仍含 bundled 定义且 Codex manifest 无覆盖项；真实配置的三条状态仍为 enabled=false，并有用户信任记录。本次配置回读没有重新证明 currentHash 匹配，也没有复测当前 TUI。

**用户澄清的目标是按宿主准确注册，保留正常审核；“让 hooks 不再需要审核”不是目标。**

| 维度 | 现状 | 后续预期 |
| --- | --- | --- |
| Codex 的 Claude-only bundled 三条 | 被发现，依靠 disabled 抑制 | 从 Codex 的定义发现源排除，hooks/list 中没有这三条 |

## 后续产品方案及验证门槛

优先使用 Codex 原生 manifest 覆盖，不先拆成两套发布包。[官方 hooks 文档](https://learn.chatgpt.com/zh-Hans/docs/hooks) 说明 manifest 可显式指定 hooks 来源；实际空值行为以本机版本实验为准。
本轮额外隔离实验仅调用 initialize、hooks/list、skills/list，使用合成插件、独立 HOME/CODEX_HOME，不启动 thread、不执行 hook、不写真实配置、不授予信任：

| 合成插件 manifest | 插件 hooks 数 | 保留的全局 hooks 数 | 插件 skill 数 |
| --- | ---: | ---: | ---: |
| 没有 hooks 字段 | 3 | 2 | 1 |
| `"hooks": []` | 3 | 2 | 1 |
| `"hooks": {"hooks": {}}` | 0 | 2 | 1 |
| 指向内容为 `{"hooks": {}}` 的专用文件 | 0 | 2 | 1 |

四种情形的全局替身均仍为 untrusted；排除不适用定义没有改变保留项的信任状态。空数组在 0.153.4 仍回退默认文件，不能用它实施修复。该实验只证明合成插件发现规则，尚不构成真实 RVF、Claude 或新版本宿主的完整验收。

推荐由 RVF 后续实施任务负责：

1. 在 Codex manifest 显式声明空 hooks 文档；保留 Claude 的 hooks 文件及入口。内联空文档改动最少；单独的 Codex 空文件表达更直观，但增加文件及引用。两套宿主发布包仅在后续确有其他差异时考虑。
2. 同步调整 installer。当前 `_bundled_plugin_hooks_document` 仍直接读取物理文件，若只改 manifest，它仍会写入 3 条已经没有定义的 disabled 状态；应停止这条过时的抑制写入，并更新测试和部署验收口径。
3. 旧 hooks.state 是状态记录，不会单独产生 hook。只在确认新宿主已无相关定义后，按 RVF selector、source、事件精确识别遗留状态，备份后迁移/清理；不删除其他 hook 的信任，不给未来定义补信任。现有 Claude 宿主识别守卫不能仅因新安装路径已分离就直接删除。
4. 真实 RVF payload 的隔离验收必须证明：Codex bundled 数为 0、6 个 RVF skills 保留、正式全局两条及其他 hooks 保留；Claude 的三条入口仍有效。覆盖首次安装、重复安装、版本更新、已有配置及新宿主 resume/fork。
5. 审核验收覆盖未审、已审、禁用、定义变化后的状态；UI 应准确解释原因，不把“没有任何提示”当通过标准。已有当前定义的有效信任应保留，变化后的定义不能沿用失效信任。

维持当前 disabled 方案可暂时保证执行被抑制，但仍暴露无用途的定义；不满足上述宿主分离目标。移除共享文件会影响 Claude；停用整个插件会再次失去 skills；仅把三条自动信任不能解决注册来源问题，均不采用。
上述产品变更尚未实施或部署。真实看板投递与完整 RVF 流程也未验收；后续先用隔离事件接收端验证，真实服务验收须属于明确的实施范围。未发现持续重装路径前，不给 Kanban 或 RVF installer 增加删除第三方 hooks 的常驻逻辑。
